## Implemented behavior

### Authorization and signer model

Ghost Gate does not pass a Tari `Proof`, call an account `*_with_auth` method, use signer/public-key badge getters, or create a resource auth-hook component. Its template argument is a `StealthTransferStatement`, verified by `StealthTransferStatement::validate`, and the template never lends proof authorization to another frame. Therefore the 0.49 proof-window instructions (`AuthorizeProof` and `DropProofAuthorization`) must **not** be added: there is no proof authorization window to open, lend, or close.

Walletd transaction construction now explicitly sets `MainSigner::SealSigner` before computing and signing the transaction. The existing builder supplies network, max epoch, nonce, fee instruction, required inputs, call, and seal signature; the selected 0.49 transaction crate computes the sr25519 signing message. No removed signer/owner proof getter remains in Ghost Gate.

### Templates and upgrade policy

All three template workspaces build against `tari_template_lib 0.37.0`. Every newly created Ghost Gate, faucet, and other-class component explicitly sets `UpdateRule::Locked`. A testnet reset is not a reason to add a new upgrade authority. Future code changes require publishing a new template and instantiating new components.

No Ghost Gate resource uses an auth-hook component, so no auth-hook component input was added. If a future resource adopts one, its component address must be declared as a transaction input under the 0.49 rules.

### Wallet statement support

The official wallet SDK still hard-coded generated stealth-output witnesses to a zero minimum-value promise. Ghost Gate needs the wallet-owned output path to carry the gate-specific public floor. The external patch:

- adds `minimum_value_promise` to `TransferOutput`;
- rejects a promise greater than the blinded amount before inputs are locked;
- propagates the value through `StealthOutputToCreate` into the output witness;
- leaves ordinary transfer and change outputs at zero; and
- adds parameter validation coverage in the upstream tree.

The patch touches only these exact-tag Ootle files:

- `crates/wallet/sdk/src/apis/stealth_transfer/params.rs`
- `crates/wallet/sdk/src/apis/stealth_transfer/types.rs`
- `crates/wallet/sdk/src/apis/stealth_transfer/api.rs`
- `crates/wallet/sdk/src/apis/stealth_outputs.rs`
- `applications/tari_walletd/src/handlers/accounts.rs`

Ghost Gate's owner-public-key derivation now supplies the owner view key required by the 0.49 wallet crypto API.

### Indexer and committed receipts

The current reader uses the official 0.50 indexer client. It supplies the new `include_proof` request field, consumes `GetSubstateResponse::into_substate_value`, and performs the bounded official decode of the base64-CBOR `Encoded<SubstateValue>`. Down, absent, malformed, non-UTXO, or unverified substates continue to fail closed.

Ootle 0.49 no longer retains call return values in `FinalizeResult::execution_results`. Ghost Gate now reads its typed `ProofReceipt` from the committed `ghost_gate.proof` event payload. Missing, malformed, or differently named events yield no attestation (zero/`None`), never a value echoed from the request.

The transitional JSON reader remains available only for explicitly selected 0.47/0.48 indexers or `GG_INDEXER_JSON=1`. Version 0.49 selects the official CBOR reader. Ghost Gate does not call the removed indexer `/utxos` route; wallet selection uses walletd's `stealth_utxos.list`, while verification fetches known substate addresses directly. No `/utxos/fetch` pagination code is required in the current paths.

### walletd, WebAuthn, hosts, and Minotari

The current walletd client types compile at 0.51.0. Ghost Gate's bootstrap login is deliberately limited to walletd's local no-auth configuration; an operator-supplied token is preserved. Ghost Gate does not register WebAuthn credentials and must not consume walletd's one-use setup token. Setup-token completion, allowed-host configuration, and wallet-to-indexer trust remain deployment-time operator work.

The live Minotari base-node gRPC reader is behind the explicit `minotari-base-node` feature. Default Ootle builds and local service tests do not require RandomX or a Visual Studio native C++ toolchain. A configured L1 gate fails closed when the binary lacks that feature. Production L1 builds must enable it and must pass the ignored live-chain tests before rollout.

Recommended CI verification is a Linux runner with adequate disk, running:

```text
cargo test --workspace
cargo test --manifest-path ../_ootle-v0492-ghost-gate/Cargo.toml -p tari_ootle_wallet_sdk minimum_value_promise
```

Then repeat the three WASM checks and the two Node suites. Do not commit or publish until those Rust suites are green.

## Remaining live-chain work

After local/CI Rust tests pass, a separate deployment stage must:

1. Reset or recreate walletd/indexer databases for the second Esmeralda reset and configure the intended indexer trust/allowed-host policy.
2. Build release WASM from the pinned cohort, publish the Ghost Gate template and only the faucet/fixture templates actually needed, and record their new binary hashes.
3. Instantiate fresh locked components; recreate all reset-invalidated resources, outputs, gate state, policy hashes, registry records, and component/resource/substate addresses.
4. Update environment-specific registry, Worker, VPS, Telegram, Sapient, and Web Tari Universe configuration only after the new addresses are verified.
5. Run live walletd/indexer receipt decoding, fresh challenge/replay refusal, gate/site/session/threshold binding, cross-resource refusal, Telegram server-side re-verification, allowed-host rejection, and wallet trust tests.
6. Build the L1 service with `minotari-base-node` only on a host with the required native toolchain, then run the ignored Minotari live-chain test.

Sapient and Web Tari Universe remain live-verification risks: the local provider contract tests are green, but only real 0.49 wallets can prove their transaction request fields, sr25519 signing behavior, frame-scoped authorization, and network reset handling.
